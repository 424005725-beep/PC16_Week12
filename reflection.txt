I designed this Smart Coffee Maker system around a layered object-oriented hierarchy so that shared hardware behavior is centralized while specialized brewing mechanics remain modular and extensible. Making _waterLevel private inside the base CoffeeMaker class enforces strict encapsulation, ensuring that water consumption and refills always pass through validation checks rather than risking invalid states. Extracting Cleanable as an abstract interface and SmartWifiControl as a mixin allowed me to keep maintenance contracts universal across all appliances while attaching network features only to smart models like EspressoMachine. Overriding brewCoffee() in both EspressoMachine and DripCoffeeMaker demonstrates polymorphism, enabling a single List<CoffeeMaker> loop to trigger distinct hardware behaviors cleanly. For error resilience and responsiveness, I wrapped user cup parsing in a try/catch block and implemented brewRemoteOrderAsync() with Future.delayed and async/await so long heating cycles never freeze the main program flow. Together, these design choices mirror real-world mobile and IoT software architecture where clean separation of concerns, defensive input handling, and non-blocking operations keep applications reliable and easy to maintain.
